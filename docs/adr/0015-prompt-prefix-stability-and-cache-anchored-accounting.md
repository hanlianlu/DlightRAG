# Prompt-prefix stability and cache-anchored context accounting

One Research request is the previous request plus new material, and so is the first request of a follow-up Run: the Session fold only appends and already states each question, each Tool's admitted evidence is frozen into that Tool's own durable result, and whatever a Run composes rides *after* the transcript. The compaction trigger is measured against what the provider billed rather than only against the character estimator, and each turn's billed prompt and cache hits are aggregated into the Run trace.

## Status

Accepted and implemented. No configuration key: this is a cost and correctness property of composition, and both values it changes (evidence reachable in the request, and evidence reachable after compaction) stay inside the retired design's own vocabulary — evidence is still citable, still one request's factual memory, and still never a summary.

Amended for follow-up Runs: the question block and the Session-notes statement moved from in front of the transcript to after it, and a replayed Tool call's arguments are serialized with sorted keys, so a follow-up Run's first request extends the previous Run's last one; a question the transcript no longer holds is restated where it stood, and a Child's instructions ride with its system prompt; a Run's first turn is now measured against its Session's previous request for the cold count, and `agent_turns` counts only the Run's own calls. The measurement that prompted it is the last paragraph of the Context; the Decision, Considered options and Consequences are revised in place.

## Context

A prefix cache is billed, not assumed. DeepSeek's context cache persists *cache prefix units* and reports `prompt_cache_hit_tokens`; a later request can only hit the cache when it fully matches a persisted unit. Measured on this deployment with one model and endpoint (`deepseek-flash`, `api.deepseek.com`):

- Agent Session `3c9f9f19` (9 turns): 505,850 prompt tokens, **0% cache hit on every turn**. `0eaa40ad` (15 turns): 1,166,820 prompt tokens, 15% hit.
- The same model in Pi: 4,695 turns, 1,506,964,818 prompt tokens, **99.71% cache hit**; average billed miss per turn 933 tokens against a 320,972-token prompt.

Two composition decisions produced that gap, and neither is about context *size*:

1. **A minute-resolution clock in the system prompt.** `core_identity()` stated `The current time is {now:%Y-%m-%d %H:%M} UTC` at offset ~60 tokens of the system message, and the Research assembler rebuilt that message on every turn. Every turn whose request crossed a minute boundary therefore began a new prompt prefix: the 9 turns above ran 1-3 minutes apart (`agentic_reasoning: max` emitted 20k-35k reasoning tokens per turn) and reported zero hits, while turns inside one minute reported 56,064 and 62,848 hits of a 63,645 and 82,466-token prompt.
2. **The evidence pack was re-rendered after the growing fold.** Every turn rebuilt the whole accumulated ledger into one trailing user message. A later request could not be a prefix of an earlier one whenever new material preceded that pack, so the pack was re-billed at the full input rate on every turn. In `0eaa40ad` the reusable prefix was only the fold — 7,680 of 76,057 tokens on one turn, 11,008 of 105,614 on another — while the 49k-90k pack was charged again. The pack also duplicated resource-backed passages that the Tool result had already shown.

The estimator is the third input to the same decision. `ContextPolicy` carries no safety margin against it and says why: the character heuristic "undercounts recorded session content by a median of 8% and up to 46%", and anchoring on the provider's reported usage was "deliberately not done here". Pi's equivalent anchors on the last assistant message's own usage and estimates only the trailing messages. Nothing in the product read `prompt_cache_hit_tokens` at all: the counters reached Langfuse as raw usage fields and no ratio, notice, or per-Run summary existed.

A third composition decision kept the same gap open across Runs after the first two had closed it within one. Authority order put the Run's question block (`user`) and the Session-notes statement (`workspace`) in front of the Session fold (`working`), and both are per Run: the block carries the question with the Run's Resource manifest and attached images, and the statement names the notes the Run bound, sizes included. Acceptance also records the question as the Run's own User Entry, so the fold already held it and every Research request stated its question twice. Measured on 2026-09-30 (`deepseek-flash`): turns inside a Run were ~92% cached, but the first request of each follow-up Run reused only its system prompt and Tool definitions — 0.8k-7.8k cached tokens of a 70k-244k prompt, ~0.95M uncached tokens across six follow-ups, ~65% of that day's uncached input. The trace hid it: every Run's first turn was exempt from the cold count and only a zero hit counted, so `cold_turns` stayed 0, and `agent_turns` counted every Assistant Entry of the Session, so a Run that made 6 calls reported 28.

## Decision

- **No system message states a clock, and each path is told where its own clock comes from.** Research reads the wall clock from its environment (`date -u` through Bash) before answering anything that depends on now, and states the date it assumes when it cannot. Fast has no tools, so its own request states the time — one line in the current message, placed before the question — and its prompt tells the model to use it. Both reference harnesses keep the clock out of the system prompt: Pi never states one, and DeepSeek's harness appends its time context as a durable user message at most every ten minutes (its `standard`, `cordis` and `ptc` presets declare the plugin, `minimal` does not).
- **Evidence text is frozen into the Tool result that admitted it.** `EvidenceLedger.take_admitted_text` renders only the rows admitted since the previous call, bounded by one absolute, model-aware observation capacity, with the batch's older rows collapsing to the re-readable handles. `ResearchRuntimeEffects` splices the result into that Tool's model-visible text, ordered so the Citation Contract's "label directly above the excerpt" holds: labels for rows the admitting Tool declared it already carries, that result, then the passages it does not. A Resource Tool answers with the passage itself (its text for `read`, its pixels for `view`) and says so with `_carried_by_tool`, which is a run-local rendering fact dropped by `_durable_row`; nothing infers it from the text. The freeze is keyed by the Effect Intent that admitted the rows, so re-executing that intent reproduces the same bytes, and `rollback_show` retracts one freeze a refused or over-long Tool result could not use.
- **No per-turn prose is composed at all.** The control instruction that restated the system prompt's own loop guidance — "call a tool only to resolve a specific missing fact; otherwise return the final answer without tool calls", already in the agent prompt, as is the Artifact reminder when that capability is on — is gone. It had to be rebuilt every turn and sat after the transcript, so the reusable prefix ended before it; neither reference harness sends anything of the kind (Pi appends only durable messages, and DeepSeek's loop derives every request from its session log). A request is now the system prompt plus the transcript, then what the Run composes, then the run-local visual lane.
- **What a Run composes follows the transcript, and the transcript states the question.** Authority order is the request order: `system`; then the transcript, `conversation` (history a stateless caller supplied, and an episodic summary) and `working` (the Session fold); then everything one Run composes, `workspace` (the Session-notes statement), `user` (the question block and a requested Skill), `profile`, `reference` and `visual`. The question block carries only what the Session does not hold — the Resource manifest and the attached images with their labels. The question itself is the transcript's: where the transcript does not hold it, before acceptance (the acceptance measure) or once a compaction has covered the Run's User Entry, it is restated where it stood — first in the transcript, right after the compaction summary — never after it, where it would follow a steer or follow-up that had since narrowed it. A Child's question is its objective, the Entry its Session records, and the instructions only a child needs (its role and scratch directory) ride with its system prompt, stable for every request of that Session. The first request of Run N+1 is therefore Run N's last request up to Run N's own statements, then Run N's answer, the new question, and the new Run's statements. Instructions and data stay apart as before: each question keeps its chronological place ahead of the Tool work it asked for and of every later steer, Tool output stays in tool-role messages, and what the Host composes rides in user-role messages of its own after the transcript, where the tool guidance and the recalled memory already were.
- **A replayed Tool call is the same bytes, in memory or read back.** `tool_call_message` serializes a call's arguments with sorted keys. A Run keeps the Entries it committed in memory, in the order the model wrote the arguments; the next Run reads them back from the jsonb column, whose object keys come back shortest first. Unsorted, a follow-up Run's first request diverged from the previous Run's at the first Tool call with more than one argument — `write`, `edit`, `search_web`, `attach_artifact`, or `read`/`grep` with options.
- **The per-request evidence pack is retired.** `ContextAssembler` no longer contributes accumulated evidence; the request is the transcript plus its trailing control instruction and clock. `observation_residual` and the pack's residual loop go with it: bounding the request is the compaction trigger's job, not composition's.
- **Evidence images keep their own lane.** `_durable_row` drops `image_data`, so pixels cannot enter the transcript the way text does. `EvidenceLedger.visual_blocks` renders them per request, bounded by the resolved image budget. This is the one place a Research request still re-renders, and it is bounded by policy rather than by corpus size.
- **Compaction keeps the compacted sources re-readable.** The framework fields `paths`/`durable_handles` were emptied when their Tool-Argument authority was withdrawn. `durable_handles` is now populated from the run's Evidence ledger — the record of what the run actually admitted — deduplicated, capped, and rendered as a list.
- **The compaction trigger is anchored on the provider.** `ContextAssembler.observe_provider_input` carries forward the gap between what the provider billed for the previous request and what this assembler measured for that same request, capped at one raw estimate, and skips requests that carried pixels because the estimator charges nothing for them by design. Only request assembly may record a measure (`accounted_input_tokens`); a measurement of a request the provider never sees — a compaction's accounted-before — reads the corrected number through `corrected_input_tokens` without moving the anchor.
- **Cache hits are observable.** `ResearchRuntimeEffects.call_provider` aggregates each turn's billed prompt and reported hits through `_record_prompt_cache` into `trace["prompt_cache"]` (`turns`, `prompt_tokens`, `cache_hit_tokens`, `cold_turns`). A turn is cold when it reused less than half of what the lane's previous Agent request billed, whether that request belongs to this Run or to an earlier one, and a cold turn warns once with the sizes. A turn has no such reference, and is never cold, when that request is older than five minutes (the shortest retention a supported provider documents: Anthropic's default cache lives five minutes, OpenAI's five to ten idle ones), when a compaction or the Session's start began the prefix, or when the request re-renders pixels after its transcript — attached images and the visual lane are billed but never reusable, and nothing counts them before the provider does, as the estimator anchor already concedes. A provider that reports no cache counters at all is not a cold turn. `trace["agent_turns"]` counts the Run's own model calls. Both counts belong to the attempt that finished the Run: each attempt's `prepare_run` starts a fresh trace, so a Run recovered after a crash reports only the calls made after its recovery, as its usage does.

## Considered options

- **Keep the clock in the system prompt at day resolution.** Rejected: it only moves the invalidation frequency from per-minute to per-day, and the same turn that crosses midnight pays the whole prompt. The clock belongs where it is cheap.
- **Freeze the clock once per Session instead of per Run.** Rejected: it moves the invalidation to the message that precedes the transcript for the *next* Run's conversation tail, and the tail is exactly what the cache is supposed to reuse.
- **Append a durable clock reading to the Research transcript when the last one is old, as DeepSeek's time context does.** Rejected: it keeps the prefix intact, but the Research prompt already tells the model to read the clock with one `date` call when a question depends on now, and no Research Run on this deployment has been seen to skip it (2026-10-03); a standing reading would add a message at the start of each Session and after every ten-minute gap to save a call that is made only when it is needed.
- **Render the frozen evidence as its own durable Session Entry next to the Tool result.** Rejected: it is the same transcript, one more entry type, and one more way for a recovery to disagree with the Tool result it belongs to. Freezing inside the result the Runtime already settles atomically keeps replay exact by construction.
- **Keep the pack for its "everything, always visible" property.** Rejected as unaffordable and partly false: the pack already collapsed to handles under budget pressure, and it was re-billed per turn while the fold stayed cached. Evidence now reaches the model where and when it arrived, and after a compaction its handles remain.
- **Make the evidence shape a configuration key.** Rejected: a switch here would keep two prompt shapes, two test matrices, and two sets of measured behaviour alive for a decision that is strictly cheaper and no less grounded.
- **Track the freeze with a plain cursor.** Rejected: a resume that re-executes an intent whose effect was still pending finds the cursor already past its rows, renders nothing, and commits the Tool's bare body without its citation labels. Keying the freeze by intent costs one small map and makes the replay reproduce itself.
- **Detect an already-carried passage by matching its text against the Tool result.** Rejected: the admitting Tool knows which of its rows its own result already answers, and a substring test misses a short body and mis-hits a long one. The Tool declares it instead, so no threshold and no heuristic exist to tune.
- **Make the control instruction durable instead of removing it.** Rejected: a durable `ControlMessageEntry` per turn costs a Session write and makes those tokens permanent in the context, to preserve a nudge whose text the system prompt already carries. Removing it is strictly cheaper and reaches the same property.
- **Move per-Run static context — memory, tool guidance, skill context — in front of the transcript.** Rejected for now as a measured non-problem: at 27 tools the guidance block is 1,999 characters (≈570 tokens) per turn, and the recalled-memory block is empty until an owner stores preferences, so re-reading the tail costs well under 1% of a 300k-token prompt while moving it would put per-Run text in front of the transcript — the placement the follow-up amendment removed for the question block — and contradict the standing-file convention that a memory block rides after the request. The run-local visual lane must stay last anyway, because it genuinely re-renders.
- **Record the Run's question material in its accepted User Entry**, so the transcript carries it and each Run reads it from the cache. Rejected: attached pixels would become durable Session content, where the Run store keeps blob references rather than bytes ([ADR 0010](0010-separate-run-blob-plane-from-operational-state.md)), and every reader of that Entry — routing and Fast's conversation view, the compaction summarizer, a Child's context snapshot, a Fork — would read the Host's framing as the user's words.
- **Place the Run's material right after its own User Entry.** Rejected: it would be cached within the Run, but the next Run no longer composes it, so the next Run's first request diverges exactly there and re-bills the whole of the earlier Run's Tool work, the bulk of the prefix.
- **State the Session notes only when they changed since the previous Run.** Rejected: knowing what the previous Run stated needs a durable record of it, and the statement is one line per note, cheaper to re-read after the transcript than that record is to keep.
- **Keep the zero-hit cold rule and only stop exempting a follow-up Run's first turn.** Rejected: the measured turns were not zero — the system prompt and Tool definitions still hit — so `cold_turns` would have stayed 0.
- **Restate a compaction-covered question after the transcript, with the Run's other statements.** Rejected: it keeps the retained work reusable by the next Run, but the Run's original question then follows a later steer or follow-up and can override it. Chronology wins; a compaction already starts a new prefix.
- **Keep a Child's objective wrapped in its instructions as its question.** Rejected: the child's Entry records the bare objective, so the wrapped question never matched it and was restated after the child's transcript on every request, behind the parent's steers.
- **Derive the tool-output bound from the compaction trigger, and share it across a batch.** Rejected after review: freezing is what keeps a passage reusable, so shrinking a frozen batch to stay under a trigger trades a permanent prefix for a turn compaction can bound anyway; and with evidence in the transcript, compaction can shrink it — which the retired pack could not. One absolute, model-aware capacity stays, and a batch may spend one per Tool exactly as Pi's absolute read/bash caps and the DeepSeek pruner's pressure-time trimming do.
- **Anchoring the estimator on the provider without the pixel guard.** Rejected: the estimator deliberately charges no tokens for image blocks, so the gap would measure the provider's image accounting and inflate the trigger.

## Consequences

A turn's request is now the previous turn's request plus its own new material, so a prefix cache can reuse everything except the newly admitted evidence and the two trailing messages. The 9-turn run above would have reused 76-88% of each prompt instead of 0% in the same-minute case and 0% across minutes for the clock reason; the two changes are independent and both apply.

Evidence text that a compaction covers is replaced by its handles rather than re-materialized, so a resumed long Run can read a source again but does not automatically re-see its passage. Compaction remains the one deliberate invalidation.

The control instruction is now present on every Research turn, including turns before any evidence was admitted; the retired composition attached it to the evidence pack, so a run that had admitted nothing sent no trailing message at all and its newest Tool observation was last. Being unconditional also makes the request shape uniform across turns, which is what the append-only property wants. The integration fixtures that read a provider request's last message to act on a Tool's own observation had to find the newest Tool result by role instead. Evidence pixels remain a per-request lane and their bytes remain run-local, unchanged in kind from before — a recovered Session still cannot re-render them, which is now stated where it is decided instead of implied by the pack.

The estimator no longer has to be honest on its own: a systematic undercount is corrected against the provider's own number, bounded so a single bad anchor cannot more than double the accounted input. `measure_control_input` stays pure for the fixed-envelope floor check; only request assembly records what the provider is about to answer.

A Tool result the durable store refuses, or one that would have been truncated, gives its frozen text back: those rows stay admitted and render with a later Tool result rather than disappearing with the refused one. Every other Tool result keeps its own evidence bytes, which is what makes the transcript replay exact.

Nothing is composed per turn. The reusable prefix is the system prompt plus the transcript, and it ends at the per-Run static tail that authority order places after it: the Session-notes statement and the question block when the Run has them, then — measured on this deployment — ~570 tokens of tool guidance plus the recalled-memory block (empty until an owner stores preferences), and then the run-local visual lane, which is bounded by the resolved image budget and re-rendered per request. The static tail is byte-stable for the life of its Run, so a later turn re-reads it rather than re-derives it. The visual lane is not reusable that way, which is why authority order gives it its own value after the tail rather than a place inside it. The transcript in front of them — the part that grows — is reused in full.

That now holds across Runs: the first request of a follow-up Run extends the previous Run's last request up to that Run's own statements, so the transcript is reusable at the start of each Run instead of only the system prompt and Tools. The price is paid inside a Run: the question block and the notes statement are re-read on every turn instead of once. Their text is small, a line per registered Resource and per note; attached images share the Run's one image budget with the visual lane, so what a turn re-reads stays within the bound this decision already accepts for that lane. A single-Run Session with many attached images and many turns pays that re-read on each turn and gains nothing across Runs; the previous order cached it inside the Run and paid the whole transcript at every follow-up instead.

A question stays verbatim once a compaction covers the Run's own User Entry: it is restated right after the summary, so every retained steer and follow-up still comes after it. That costs the next Run some reuse: its own question is in the transcript, so the covered question is not restated there, and its first request diverges from the compacted Run's right after the summary — in a probe, 2 of 5 messages matched, against 4 of 5 with the question restated at the end. Compaction is rare and already starts a new prefix, and a question that overrides a newer steer is a wrong answer rather than a cost. "The transcript holds the question" compares the User message the Host accepted with that very string, not a text search, and an earlier identical question cannot stand in for a covered one, because a compaction keeps a suffix and the Run's own Entry is newer. A Child now states its objective once, as the Entry its Session records; its instructions ride with its system prompt ([ADR 0025](0025-a-child-inherits-capability-not-authority.md)).

The Session-notes statement now follows the Run's own writes, so it dates its sizes to the start of the Run rather than presenting them as current.

A known residual predates this amendment: a Session's first Run that received a caller's `history` or `episodic_summary` shares only the system prompt with the next Run, because the executor stops injecting caller history once the Session holds turns of its own.

A Fast answer states its clock in its own request, which is exactly where that costs
nothing: a composed current message is fresh every turn and never enters the reusable
prefix, and Fast's reuse comes from the system message and the durable history pairs
in front of it.

A recovered Session starts a fresh assembler, so its first turn is measured by the
estimator alone and the anchor resumes after that turn. A compaction measures the
request it was decided from without recording it, so the next anchor keeps comparing
the provider's billed count against the request that was actually sent.

Stop conditions, to revisit this decision rather than extend it silently: a provider whose cache prefix units do not match append-only requests; evidence batches regularly saturating the observation capacity so that most passages arrive as handles; the visual lane growing past its image budget; a measured Run where the anchored trigger compacts before the provider's own limit would have required it; a deployment whose Research environment disables Bash, where the agent has no way to read a clock at all; a batch whose frozen results routinely push a request past the trigger and make compaction frequent, which is the case the retired per-batch share would cover; a follow-up Run whose first turn counts as cold while the transcript it extends is unchanged; or Runs whose attached images, re-read on every turn, cost more than the transcript their order saves.
