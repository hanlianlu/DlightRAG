# Research: MinerU sidecar floor 3.4.4 → 3.4.5

## Summary

Adopt MinerU **3.4.5 as DlightRAG's minimum sidecar version**, because it contains two narrowly scoped parse-artifact correctness fixes that can improve the text LightRAG later chunks: DOCX table text now preserves special OOXML characters, and PDF text now restores supplementary-plane Unicode represented by UTF-16 surrogate pairs. The upstream patch does not change MinerU's API, Python range, dependencies, extras, or configuration surface, so DlightRAG should **not add a new MinerU setting** for this upgrade; keep the current parser/VLM ownership split and existing corpus-dependent `high`-effort opt-in. [Official tag list](https://api.github.com/repos/opendatalab/MinerU/tags?per_page=20) · [official comparison](https://github.com/opendatalab/MinerU/compare/mineru-3.4.4-released...mineru-3.4.5-released) · [PyPI 3.4.4](https://pypi.org/pypi/mineru/3.4.4/json) · [PyPI 3.4.5](https://pypi.org/pypi/mineru/3.4.5/json) · local `pyproject.toml:8-26`, `src/dlightrag/rag/settings.py:62-101`, `docs/configuration.md:40-142`.

## Findings

1. **Medium — 3.4.5 is an artifact-correctness patch, not a feature/config release.** The official tags identify `mineru-3.4.4-released` as `0dfc9460cd9ab693b9af60ae3fbffd7bc111b062` and `mineru-3.4.5-released` as `fbb1257a555a3fde78ae5aaaa931e3b3f8fb2883`; the official compare contains six commits across five files, with the two runtime changes below plus focused tests. [Official tags API](https://api.github.com/repos/opendatalab/MinerU/tags?per_page=20) · [official compare](https://github.com/opendatalab/MinerU/compare/mineru-3.4.4-released...mineru-3.4.5-released).
   - `mineru/model/docx/docx_converter.py` preserves non-breaking hyphens, soft hyphens, and `w:sym` characters while matching native OOXML table text against Mammoth HTML; when a table conversion still fails, its warning now includes the exception instead of silently losing the diagnostic. This matters before LightRAG: corrected table characters become part of the parser bundle that is subsequently chunked/indexed. [3.4.5 source](https://github.com/opendatalab/MinerU/blob/mineru-3.4.5-released/mineru/model/docx/docx_converter.py) · [compare](https://github.com/opendatalab/MinerU/compare/mineru-3.4.4-released...mineru-3.4.5-released) · local parser ownership description `docs/configuration.md:50-101`.
   - `mineru/utils/pdf_text_tool.py` reconstructs valid UTF-16 high/low-surrogate pairs returned by PDFium, preventing supplementary-plane code points from becoming replacement characters. Those corrected code points likewise enter the content before LightRAG extraction/chunking. [3.4.5 source](https://github.com/opendatalab/MinerU/blob/mineru-3.4.5-released/mineru/utils/pdf_text_tool.py) · [compare](https://github.com/opendatalab/MinerU/compare/mineru-3.4.4-released...mineru-3.4.5-released) · local ingestion boundary `src/dlightrag/rag/settings.py:250-263,366-390`.

DlightRAG's separate `MINERU_PYTHON=3.13` environment therefore remains necessary and valid while the main application stays on Python 3.14, and the existing `core`, `core,mlx`, `core,vllm`, and `core,lmdeploy` installer choices need no change. 3. **Medium — update the floor and reinstall existing sidecars.** Change the checked-in floor and exact-pin example from 3.4.4 to 3.4.5. Keep the reviewed API range below 4 so a normal `-U` run cannot silently cross into an unvalidated major; an exact pin is combined with, rather than allowed to override, those compatibility bounds. The change affects fresh/generated environments and upgrades when `make mineru-install` is rerun; it does not mutate an already installed `.venv-mineru` merely because the repository default changed. [PyPI 3.4.5](https://pypi.org/project/mineru/3.4.5/) · local `.env.mineru.example`, `scripts/mineru/install.sh`, `Makefile`.
   - Existing untracked `.env.mineru` files may still explicitly set `MINERU_MIN_VERSION=3.4.4` or `MINERU_VERSION=3.4.4`. The operator-facing upgrade note tells users to update/remove those values and rerun `make mineru-install`; an incompatible exact pin now produces an unsatisfiable package requirement instead of bypassing the project floor. The setup wizard only maintains `MINERU_INSTALL_EXTRAS`, not the version policy, when configuring a local parser.
   - No root dependency or lockfile change is needed: MinerU is intentionally isolated from the Python-3.14 DlightRAG application, whose RAG dependency is `lightrag-hku`, not `mineru`. Local `pyproject.toml:8-26`, `README.md:63-79,106-115`.

4. **Medium — the fixes land on the correct side of DlightRAG's LightRAG boundary.** DlightRAG owns typed sidecar selection and translates it to LightRAG's parser rule (`*:mineru-iteP`) plus `MINERU_*` variables; LightRAG remains the engine that requests/validates the external parser bundle and turns it into chunks, images, tables/equations, and later KG/vector inputs. Therefore the two upstream corrections should not be reimplemented in DlightRAG, but affected already-indexed PDF/DOCX sources must be explicitly reparsed/reingested to replace old artifacts and derived indexes. 5. **No new MinerU configuration should be adopted now.** The 3.4.5 comparison adds no option or changed default. Keep `backend: hybrid-engine`, keep the OCR hint independently selected for the corpus, keep loopback binding, and leave MinerU image analysis off. Continue offering `MINERU_HYBRID_EFFORT=high` only for figure-heavy corpora where better whole-figure/caption crops justify the documented throughput cost; it is not a 3.4.5 migration requirement. Validate the corrected DOCX path manually through LightRAG's real local-client boundary and the PDF helper against the installed wheel; do not duplicate MinerU's own low-level fixtures in DlightRAG when the bundle protocol and IR shape did not change. ## Implementation and validation outcome

- Raised the checked-in installer and example floor to 3.4.5, bounded automatic upgrades below 4, kept exact pins inside that supported range, and added operator-facing migration guidance plus regression assertions.
- Upgraded the active Apple Silicon `core,mlx` sidecar environment, restarted both launch agents, and confirmed both distribution metadata and `/health` report 3.4.5 with protocol version 2. Because the installer uses an unconstrained `-U` solve, this operation also refreshed transitive packages; the compatibility and parse smokes below passed afterward.
- Loaded DlightRAG's `sitecustomize.py` against the installed 3.4.5 package, proving the keep-alive, title-prompt, and hybrid-effort compatibility shim still imports.
- Exercised the real LightRAG 1.5.6 `MinerURawClient` against the local 3.4.5 `/tasks` API with a DOCX table containing a non-breaking hyphen; the downloaded `content_list.json` preserved `NCI‑CTCAE`.
- Exercised the installed 3.4.5 PDF surrogate-restoration helper with PDFium UTF-16 units and confirmed it reconstructs the supplementary-plane character `𝜃`.
- Affected historical sources still require explicit reparse/reingest; upgrading the installer cannot rewrite already-derived LightRAG chunks, vectors, KG, or provenance artifacts. Local `README.md:341-367`, `src/dlightrag/rag/settings.py:250-263,366-390`.

## Gaps and residual risks

- The release tag is stale, but the PyPI wheel's module and distribution metadata both report 3.4.5. A running PyPI installation that still reports 3.4.4 from `/health` is therefore still the old process or old environment and should not be waved through.
- The PDF correction was validated at MinerU's extraction-helper boundary rather than with a newly authored font-embedded PDF fixture; upstream's focused regression test owns the low-level PDFium case, while DlightRAG's relevant integration boundary is the unchanged LightRAG bundle protocol.
- The report confirms the two checked-in floor literals from the inspected repository. Run `git grep -n '3\.4\.4'` before implementation to catch test fixtures or newly added files not present in this research snapshot.
- The supported range permits future compatible 3.x MinerU releases while rejecting 4.x until its API is reviewed. `MINERU_VERSION=3.4.5` narrows MinerU itself but does not lock its transitive environment: the real upgrade refreshed multiple compatible dependencies even though MinerU's declared dependency set was unchanged. A bit-for-bit reproducible sidecar would need platform/extra-specific lock artifacts; that is packaging work, not a MinerU or LightRAG product-config knob, and is deferred from this narrow patch.
